# Stark website

A static landing page: HTML, CSS and a small browser script, with no package installation, server-side code, analytics, external fonts or model execution. The logo is the owner-supplied image recorded in [brand provenance](../docs/brand/README.md).

## Build and preview

From the repository root, with Node installed:

```sh
node website/build.mjs
python3 -m http.server 4173 --bind 127.0.0.1 --directory website/dist
```

Open `http://127.0.0.1:4173`. `public/` is the source and `dist/` is ignored generated output. From a standalone site checkout, run `node build.mjs`.

For a local review, serve the built files from the feature branch and share the loopback URL. Building and previewing do not publish the site. Changes to the hosted site use the separate publication workflow below.

Release copy is evergreen. Download and release-note links use GitHub's stable `releases/latest` URLs, so publishing a release requires no website rebuild. Update the site when installation steps, compatibility requirements or feature claims change. Benchmark, validation and provenance references stay pinned to the source revisions behind their evidence.

## Content and interactions

- The hero introduces free, open-weight models and connecting apps for coding, writing and everyday tasks, with the owner's requested local-privacy copy. The privacy section explains the separate data practices of connected apps and tools. Its CTA links to the latest signed, notarized Mac app and the product walkthrough. “Open source” describes Stark's engine; downloadable model weights are open-weight and individual model licenses vary. The page retains the large original cat artwork without placing upstream provenance copy above the download CTA.
- The product walkthrough uses three owner-supplied PNG screenshots: `public/assets/stark-guided-setup.png`, `public/assets/stark-model-catalog.png` and `public/assets/stark-playground.png`. They show guided setup, the model catalog and Chat mode, without the computer-use indicator. Original PNG bytes and transparency are preserved. Each links to its full-size image. The [replacement record](../docs/archive/runs/2026-11-06-website-screenshot-replacements.md) records dimensions and hashes.
- The product walkthrough explains the app/model distinction and the relationship between Stark, OpenWork and OpenCode Desktop. Beginner checks Mac resources and offers estimated recommendations; Advanced covers model imports, settings and the catalog. Both modes share installed models and can be switched later. The setup guide covers installing Stark, choosing and starting a model, chat and optional desktop-app setup. An expandable Terminal installer remains available for the app plus CLI tools.
- The model section gives memory guidance: the two built-in Qwen3 starters require 16 GiB, while Beginner checks other eligible catalog suggestions model by model, including on Macs below 16 GiB. It describes the starters' 32K context and estimated runtime memory, and explains that model downloads need additional room. These values are planning estimates, not per-Mac guarantees; details and qualification are in the [hardware/model review](../docs/archive/runs/2026-11-05-hardware-model-recommendation-review.md).
- Pinned Qwen3 starter cards and model-family entries show capability badges for reviewed tool templates, conditional support or unavailable tool calling. These are template-support indicators; a model family name does not guarantee tool use. Users are directed to check “Tool use available” in Stark. The inventory includes Text, Images and Decision tabs, expandable checkpoint families and links to compatibility, preparation and validation records. Tabs support arrow keys, Home and End, direct panel fragments, roving keyboard focus, and remain readable without JavaScript. The Qwen3.8-27B mixed 4/5/6/8-bit checkpoint is available in Stark 0.16.5 and newer under Advanced → Model Catalog → Qwen3.5 dense; it has no dedicated website benchmark panel.
- Image support is documented for one PNG/JPEG through Playground, terminal chat and the Local API with admitted dense BF16 Qwen3.5 vision artifacts after local checks. Qwen3.8-Flash-Next is identified as text input. Family constraints and validation scope remain in linked documentation.
- The JevK5 feature says: “Use a Jev-like decision model in Playground's Decision mode. Stark runs the open-weight JevK5 4B BF16 model locally.” It links to the scoring evidence for technical details and validation scope.
- The Apps section covers OpenWork for everyday files and OpenCode Desktop for coding, each with official download links and setup guides. Both connect through Stark's Connections → Apps without copying an API key. The steps describe OpenWork workspace and relaunch requirements, OpenCode per-engine approval, keeping Stark open, reviewed template/tool-capable models and small first tasks. App tabs support arrow keys, Home/End and direct `#openwork-guide`, `#opencode-guide` and `#engine` links; all panels remain readable without JavaScript. These integrations do not establish general agent reliability; connected apps and enabled plugins have their own data practices.
- A local-privacy section explains on-device inference, app/API boundaries and the lack of site-authored analytics or advertising trackers, system fonts and the hosting provider’s security checks. It also states that model downloads use the internet and that connected apps, plugins and tools may access external services. The Integrate Stark reference documents loopback HTTP, capability discovery, worker JSON-lines framing/readiness, request limits, authentication and scoring semantics; no SDK packages are published. Direct worker hosts own their templates, tool execution and agent loop.
- HTTP, Generate, Score and Convert examples show request shapes and commands but do not execute in the browser. Tabs support keyboard navigation; examples can be copied with a selection fallback. Placeholder tokens and credentials are used. The HTTP notes point to Stark's generated curl example, which avoids putting the key in argv or environment variables.
- A follow-up section compares a pinned synthetic Qwen3-4B 4-bit baseline worker with a prefix-reuse candidate: 7.6–8.6 seconds versus 0.6–1.4 seconds of follow-up prompt processing for roughly 19–21K-token prompts on an M5 Max. Baseline and candidate are separate builds, though they use the same checkpoint and matched setup; output hashes matched in recorded cases. These are worker prefill timings, not full response times. The first request still processes its full prompt, and results do not generalize to other hardware or workloads. The [run record](../docs/archive/runs/2026-11-06-website-product-story.md) links the source-bound test and current reuse contract. A separate live OpenWork session remains illustrative, not a controlled comparison, and is not used for the page's numeric claim.
- The benchmark section retains three keyboard-operable tabs, with all panels readable without JavaScript: the Qwen3.8-Flash-Next comparison, Qwen3.8 MTP study and Qwen3.5-2B multi-engine study. The Qwen3.8 study reports 66.81 versus 61.17 tok/s (9.2% higher maximum observed decode) against MLX-Serve 26.10.3, using identical checkpoint files and quantization without speculation. It records the closed-app condition, request range, 255-useful-output timing convention and lack of established whole-model numerical/quality equivalence. The immutable report and `public/benchmark-qwen38-results.json` provide details.
- The 31 October MTP tab compares enabled versus disabled within two distinct Qwen3.8 checkpoint packs using 4,096 input tokens, 256 sampled outputs, top-k 20, two drafts and exact sampling: Lily Q4-XL 82.85/72.97 tok/s (+13.54%) and mixed 4/8-bit 65.02/56.69 tok/s (+14.69%), each from 16 pairs. Lily nucleus sampling without top-k gained 1.70%. It records separate study windows and timing drift, notes MTP is off by default, and does not present these as a new MLX comparison or a general throughput floor. The tab links immutable reports and the aggregate copies `public/benchmark-qwen38-mtp-lily-results.json` and `public/benchmark-qwen38-mtp-mixed48-results.json`.
- The Qwen3.5-2B study covers six workloads across six configurations and five engines. Its default view is tokens per second; relative mode normalizes MLX-LM to 1.000× from unrounded rates. The semantic table remains available without JavaScript, and narrow screens scroll it within its own region. Expandable methodology covers repeated loads and requests, complete request timing, transport differences, quantizer differences and qualification limits. The 12.2% result remains scoped to that study; exact revisions, answer-format checks and workload definitions are in the immutable report. Result JSONs are copies of canonical aggregate records under `docs/benchmarks/data/`.
- Focus indicators, image descriptions, reduced-motion handling, keyboard-operable tabs and a skip link support accessibility. The page declares a light color scheme; benchmark panels use a light background with dark text and muted gold accents. There is no theme switch.
- `robots.txt`, `sitemap.xml` and `404.html` ship beside the page. The site is one document, so the sitemap lists one URL. The 404 page uses absolute asset paths and is marked `noindex`; whether unknown paths return an HTTP 404 status depends on the hosting platform.

When a benchmark changes, update its corresponding result JSON, pinned report links in `public/index.html`, and the [benchmarks index](../docs/benchmarks/README.md) together. Qwen3.5 uses `public/benchmark-results.json`; the no-speculation Qwen3.8 comparison uses `public/benchmark-qwen38-results.json`; the Qwen3.8 MTP panels use `public/benchmark-qwen38-mtp-lily-results.json` and `public/benchmark-qwen38-mtp-mixed48-results.json`. These are byte-identical copies of their canonical aggregate records under `docs/benchmarks/data/`.

## Hosting

The site identity is in `.openai/hosting.json` (a deployment project identifier, not a secret), with `dist` as the static directory. The public URL is [starkengine.app](https://starkengine.app/), which is also the canonical URL; [starkengine.io](https://starkengine.io/) serves the same site. Publication mirrors only the website source into a separate ignored checkout, builds it, and uploads `dist/` with the hosting manifest; credentials are supplied through the workflow's stdin and never stored. The domain setup and the first deployment are recorded in [the deployment record](../docs/archive/runs/WEBSITE_DEPLOYMENT_2026_10_21.md).
