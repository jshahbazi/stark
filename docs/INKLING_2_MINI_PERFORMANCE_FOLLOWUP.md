# Inkling 2 Mini performance follow-up

Planning review, 2026-11-21. Baseline is the original checkpoint on `34b25508` and the 128 GiB M5 Max. The measured cold 4K worker baseline for future comparisons is about 6.0 s, or 683–685 tok/s, with vision and DSpark resident and drafting off. Its useful decode medians were 31.38 tok/s greedy and 30.31 sampled. The ideas here are proposals. ## Prefill

Start with attribution on the current worker schedule. The detailed 9.147 s graph assigned 2.994 s to NVFP4 products and 0.069 s to activation quantization and ingress. That makes projection work a stronger lead than more quantizer microtuning. The profile belongs to the earlier eight-route packed graph. The current 2,048 + 2,044 + 3 schedule and source kernels can change every stage share. The existing packed profiling entry assigns a diagnostic workspace without enabling the worker's source mode, then takes its tile width from the session. This can cap a 2,048-row diagnostic at 512 rows, and its uniform chunk loop does not reproduce the three-row tail. A future profiling run should compare the actual bulk chunks, short tail and seed, validate its logits against an uninstrumented run, and collect per-stage GPU time separately from cold worker throughput. A single stage would need about 29% or 63% of the current wall budget, respectively, even if it could be doubled. Those are planning thresholds. Every candidate needs the current phase attribution before any throughput estimate.

Retire pure layer reordering, larger geometry alone, four-query K/V sharing, prior guard and register-only variants, and FP4 midpoint microtuning as first attempts. Those arms either tied, lost, or failed numerical qualification on the graph they were screened against. Contexts above 4,352 and image or draft-enabled prompts currently fall back. Improving those workloads is a separate coverage decision with its own memory, supported-mode and cache tests. Prefix reuse already gives a major warm benefit and stays a separate metric from cold throughput. ## Decode

### Recover the measured singleton regression first

The source-aligned path lost about 6% useful decode throughput in the matched worker run. The medians imply a gap of roughly 1.8 ms per token for both samplers. The 28.030 ms synthetic incumbent step uses one command and one wait, and its seeded cache, vocabulary readout and timing boundary differ from the full worker. Use the actual source-mode worker to profile projections and relative attention, the router, NVFP4/MXFP8, cross-pass work, vocabulary readout and host sampling. Split ordinary token steps from process startup, first-sample time, and streaming/cancellation overhead. A controlled same-state replay can locate the expensive difference, with the source-mode logits and committed state as the reference for any candidate. [Worker benchmark](benchmarks/2026-11-21-inkling-mini-native-worker.md#source-aligned-m5-max-prefill) · [Final trace and synthetic control](model-experiments/2026-11-21-inkling-mini-packed-prefill.md#20261121-inkprefill-09--source-aligned-worker)

The highest-value serial candidates are the stages that changed when preserving Ollama singleton parity. Look at the TF32 router projection and relative-table tensor product, K/V handling and expert math before changing the scheduling structure. The singleton router already removed four dispatches per visit. Inkling also already has the one-command design that produced the early Qwen graph gain. Preserve the source reduction order and test short and 4K head, cache and convolution boundaries after any replacement. If the current measurement points to launch cost, consider merging adjacent exact operations, such as expert output reduction and its consumer, only where it removes a dispatch or a scratch round trip. Lily's comparable fusion saved 5.6% in a component and left whole-model speed within noise. ### Largest credible gain is a verifier that can skip target work

The present DSpark path proposes one token from its eight-row draft block, runs the ordinary target step, samples once and counts agreement. It skips zero target forwards. The short fixed build took 0.635 s with its serial verifier against 0.467 s draft-off, with 10 agreements in 15 proposals. The next candidate would run the ordinary target arithmetic for the anchor and candidate in one two-row verify pass, then commit or discard the candidate state. The existing bulk prefill path emits only its final logit row and has separate arithmetic. Lily's own prefill kernels failed its verifier parity gate, while a batched form of its decode kernels passed. Share weights and dispatches across verify rows only where each row retains the target rounding order. [Inkling DSpark attempt](model-experiments/2026-11-21-inkling-mini-dspark.md) · [Current serial verify loop](../crates/stark-generate/src/inkling.rs) · [Lily verifier history](PERFORMANCE_PLAYBOOK.md#5-speculative-decoding)

For one proposal, let `T` be ordinary milliseconds per committed token, `D` the proposal time, and `p` the probability the target's ordinary draw agrees. The verifier plus commit, rollback and host work must cost less than `T × (1 + p) − D` to break even. The short Inkling values of 29.17 ms, 5.20 ms and 10/15 give **43.4 ms** to break even and **39.0 ms** to gain 10%. These numbers are an illustration from one short diagnostic. Measure acceptance and marginal verify-row cost at 4K on code and prose, greedy and sampled, before choosing a schedule. Use the same target arithmetic in the serial and verify arms and also compare end-to-end with the currently shipped draft-off worker. Enabling DSpark currently changes prefill eligibility.

Keep the current target sampler and random draw order for accepted and rejected rows. Compare both verify rows and the next committed token with serial, including local ring wrap, global KV appends, all four convolution histories per visit, the committed taps and DSpark state. Exercise full acceptance, rejection, EOS, cancellation, draft-mode and prefix restoration. Only then assess a whole-request speed claim. Deeper and adaptive drafts from Lily become useful after a one-proposal round pays on real workloads. Prompt lookup is another proposal source for copied code or tool output once the exact verifier exists. Lily gained 8–10% on copy-heavy greedy tests. Lookup moved its twelve-cell schedule score by 0.3%. Use a normal serial token when the planner chooses zero drafts. [Lily round costs and prompt lookup](PERFORMANCE_PLAYBOOK.md#the-round-model)

### Bounded host and readout follow-ups

- Inkling already uses the shared host sampler, including the vectorized greedy path and ordered F64 probability accumulation. Each target step still copies and finite-checks all 200,058 F32 logits. If measurements show meaningful cost, consider avoiding the copy or returning an exact greedy token and validity flag from the GPU. Preserve softcap behavior, the first maximum on ties, signed-zero and subnormal handling, and the existing nonfinite failure path. Keep full-F32 readout for sampled requests unless an exact sampling proof and seeded replay justify a different path. [Current readout](../crates/stark-engine/src/engine/inkling_slice/session.rs#L654) · [Shared sampler](../crates/stark-generate/src/hybrid.rs#L1122)
- Compare wait strategies only if the measured host wait warrants it. Lily's polling win was on the long verifier, about 2 ms per round. Polling lost on its earlier serial loop. Treat the idle keepalive as first-token latency work and measure Inkling before assigning it value. A narrower weight pack, KV quantization, or a different attention math policy would require separate numerical and artifact qualification. [Host round trips](model-experiments/2026-11-19-lily-mtp-host-roundtrips.md) · [Idle and cadence](PERFORMANCE_PLAYBOOK.md#9-idle-wake-cadence-and-host-conditions)

If execution is approved, measure stock prefill and source singleton attribution together on the current worker. Then choose one measured serial bottleneck to recover the regression. Treat the exact two-row DSpark verifier as the higher-upside follow-up with its own correctness and round-cost gates.
