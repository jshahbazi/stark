## Hypothesis and change

- Concrete problem, trigger and expected behavior: admit Base Labs
  `baselabs/elephant-1` as a Decision-only Stark model without converting its
  task-specific checkpoint into an ordinary causal chat model.
- Baseline and candidate difference: the existing Decider route executes a
  separate BF16 255-row head under globally noncausal full attention. Elephant
  uses the OneJev `qev-labels-v2` prompt, 256 unique slot tokens in a
  separately loaded F32 output readout, block-bidirectional full attention,
  causal DeltaNet layers and a 16,384-token limit.
- Correctness metrics, fixed thresholds and controls: native block masking must
  prevent the state prefix from reading future question tokens and let both
  blocks attend bidirectionally within themselves. Exact artifact choices and
  probabilities must be compared with the pinned OneJev source before
  qualification; no tolerance is promoted from another checkpoint.
- Distinguish qualification artifacts and implementation sources: the artifact
  is Elephant at `b3f8a93462fb1051a9de031e94a7ff380e254072`; the protocol source
  is OneJev at `81ce62f1597c91e46767d4d02d6ac2e18534fe94`.
- Why the attempt was stopped: full 9B artifact numerical, image, memory,
  lifecycle and performance runs are separate gates from source-aware
  implementation.

## Follow-up history

### ELEPHANT-01E: bounded prefill wide-SIMD acceleration

- Trigger: a synthetic single-question test took multiple seconds even before
  request rendering or readout, and phase metrics identified model prefill as
  the dominant cost.
- Build identity: `stark-decide` SHA-256
  `3eb309e7afcc9e3e1f8bbba16b9356be68d943eb6b4ec9651285feca3261b3f8`,
  Rust 1.98.1, Apple arm64.
- Change: Qwen3.5 reference-prefill linears use Stark's existing MLX-adapted
  32-lane BF16 dot kernel for row batches of two or more. A prefill wider than
  1,024 rows is partitioned into bounded dispatches. One-row readout and
  unrelated numerical profiles keep their prior path.
- Rejected alternatives: group64 Q4 weights were 20-50% slower on Apple M5
  Max in a bounded 89-token trial; the generic BF16 GEMM policy was about 2x
  slower while producing the same tested slot logits; and disabling DeltaNet
  reference arithmetic did not materially improve latency. Those candidates
  were not adopted.
- Scope and controls: the same exact 9.4B prepared BF16 artifact, worker
  protocol and synthetic inputs were used for baseline/candidate runs. The
  final repeated run used 113 raw text tokens (3 samples), 526 raw text tokens
  (2 samples), and one 32x32 PNG request (1 sample), with each worker loaded
  once and samples serialized.
- Result: median worker wall time changed from 3.5059 s to 2.7908 s for
  113 tokens, 19.2725 s to 12.7413 s for 526 tokens, and 7.0767 s to 4.8029 s
  for the one-image control. The selected slot was unchanged. The 113-token
  and image slot logits were bit-identical; the 526-token slot logits differed
  by at most 0.0625 and 0.025 mean absolute raw-logit units.
- Correctness and promotion: a 1,025-row component test passed on both native
  backends within one BF16 output step of the scalar schedule, and repeat
  samples preserved the selected slot. This is bounded performance evidence
  for the exact BF16 artifact, not upstream source parity or broad quality
  qualification.
- Follow-up gate: compare checkpoint choices/probabilities with the pinned
  OneJev reference, then repeat matched performance on longer image/text
  workloads and other Apple GPU families.
