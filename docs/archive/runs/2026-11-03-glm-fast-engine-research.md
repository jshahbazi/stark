# GLM-5.3-Flash fast-engine research

Date: 2026-11-03. Status: read-only research; no local model runs, installs, wired-memory changes, engine edits, or performance qualification.

## Findings

The most useful Apple Silicon references are **oMLX's dedicated GLM prefill kernels** and **mlx-serve with mlx-stream's exact-model M5 Max streaming implementation**. Both explicitly implement `glm5_next`, including KDA, pooled sparse MLA, mHC, and routed experts. llama.cpp is the nearest GGUF baseline. gmlx is another exact-model GGUF candidate, although its published benchmark tables inspected here contain no GLM row. These are candidates for a controlled comparison; the sources do not establish which engine is fastest with Stark's artifact.

The likely transferable work is wider packed matrix multiplication and expert grouping during prefill, bounded asynchronous submission, fused mHC/KDA preparation, and sparse attention over selected latent rows. MTP improves decode when acceptance amortizes verification; it does not explain a cold prompt's prefill speed.

The target context supplied by the active Stark work is an M5 Max with 128 GiB, macOS 26.7.1, and `unsloth/GLM-5.3-Flash-GGUF` UD-Q2_K_XL, approximately 101 GiB. Historical optimized short-prompt GLM decode was around 35 tokens/s; the external same-box streaming result below is around 33 tokens/s under different conditions. That makes prefill/TTFT the first investigation target, without establishing a decode ranking. Stark's optimized long-prefix validation is still separate local evidence. No external number below uses its complete configuration. The supplied CPU profile was taken from the default-settings run; waiting in Metal command completion cannot by itself separate GPU compute from synchronization or submission cost, or characterize the optimized run.

## How the Apple fast paths work

### 1. Keep enough useful work in each prefill matrix operation

oMLX sorts token routes by expert, then builds tiles that contain one expert's contiguous row run. This avoids a tile repeatedly walking the weight matrix with most rows masked for other experts. `sorted_gather_qmm` selects segmented or double-buffered weight loading and tile sizes from rows per expert and shape. `sorted_gather_qmm_swiglu` additionally performs clamped gate/up activation in the epilogue; a row map can read the original token rows instead of copying each activation once per selected expert. Packed weights are dequantized within the tile rather than expanded as a complete model-wide float matrix. Eligibility is specific to affine 4/8-bit or MXFP4 and BF16/FP16 activations; UD-Q2_K_XL needs its own packed layout and numerical policy. [Implementation](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/m5_gather_qmm_nax.py), [merged PR #3995](https://github.com/jundot/omlx/pull/3995).

The earlier gate/up fusion concatenates compatible weights at load and uses one matrix operation. It skips incompatible formats and expert offload. Wider prompt chunks increase tokens per expert: GLM top-8 / 288 experts averages about 57 routed rows per expert at 2,048 tokens and 228 at 8,192, before routing imbalance. oMLX's PR explicitly records additional memory and coarser prefix-cache granularity. Chunk size is therefore a joint compute, workspace, and reuse decision. [PR #3993](https://github.com/jundot/omlx/pull/3993), [PR #3988](https://github.com/jundot/omlx/pull/3988).

### 2. Bound synchronization while allowing host and GPU overlap

`LayerPipeline.push` queues with `mx.async_eval`; it waits on the oldest work once the bounded depth is reached. The GLM model uses it to construct the next layer while the GPU executes the prior layer, keeping cache-release behavior through an evaluated hook. Its lazy-last option leaves unneeded final-layer output work unevaluated when the caller only consumes prompt caches. Stark must first establish whether equivalent stalls or unnecessary work occur in its Rust/Metal path. Merely increasing command-buffer size does not reproduce a dependency-aware pipeline. [Source](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/utils/layer_pipeline.py), [PR #3971](https://github.com/jundot/omlx/pull/3971).

### 3. Fuse mHC and KDA preparation, retaining sensitive state precision

oMLX `hc_pre` fuses F32 RMS, the small mixer, Sinkhorn, and collapse; `hc_expand` fuses the residual expansion. Fixed per-row reduction structure prevents chunk size from changing results. This path avoids repeated large temporary casts and small separate operations. The PR distinguishes exact-F32 reference equality from M5 default TF32 behavior. [Source](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/mlx_vlm_glm5_next_compat/vendor/mlx_vlm/models/glm5_next/hc_prefill.py), [PR #3983](https://github.com/jundot/omlx/pull/3983).

KDA `glm53_kda_prefill` uses fused convolution/SiLU/L2 preparation and output norm/gate. `kda_recurrence` holds F32 recurrent rows in registers, stages several tokens' inputs, and computes the forget gate inside the recurrence. It removes the materialized F32 gate tensor. Current eligibility requires BF16 input and F32 recurrent state. This is a different activation policy from Stark's F32 reference. Reduction-order changes can alter near-tied logits even while the recurrence formula is unchanged. [Preparation](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/glm53_kda_prework.py#L216), [recurrence](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/glm53_kda_recurrence.py), [PR #3984](https://github.com/jundot/omlx/pull/3984).

**40-core detail:** oMLX's default per-core plan requires at most 128 value rows per core. GLM's 64 × 128 rows exceed that on 40 cores, so it falls back to blocked recurrence. mlx-stream's `planFor` explicitly allows two groups per core: 40 cores get 80 groups with a maximum 104 rows each. Its tests cover row partitioning and F64-reference comparisons. This is a useful independently implemented schedule candidate; it still needs Stark qualification. [oMLX gate](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/glm53_kda_recurrence.py#L364), [mlx-stream plan and tests](https://github.com/davidtai/mlx-stream/blob/ac3b772b61bce66450862bca697dbb742c35453f/src/arch/glm5_next/kda_percore.zig#L49).

### 4. Run sparse work over selected latent rows

oMLX `indexer_scores_nax` uses BF16 products with F32 accumulation, applies per-head weighting and causal pool masking, then selects pools. `sparse_mla_attention_nax` reads selected rows through indices without first materializing all gathered keys, performs online softmax, and keeps probability multiplication precision through split high/low FP16 pieces with F32 accumulation. The implementation deliberately avoids relaxed tensor precision. These are mostly long-context prefill ideas: the model already bypasses sparse selection while the causal prefix fits the selection budget. A short 1,221-token prompt cannot demonstrate the large-pool indexer's asymptotic benefit. [Indexer](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/glm_moe_dsa/indexer_nax.py), [sparse MLA](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/glm_moe_dsa/sparse_mla_nax.py), [GLM call sites](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/mlx_vlm_glm5_next_compat/vendor/mlx_vlm/models/glm5_next/language.py#L1369).

gmlx offers a separate implementation: `_streamed_absorbed_attention` computes attention over compressed latent keys in bounded query/key tiles with F32 online softmax and explicit dependency edges; `_gathered_sparse_prefill` selects a union of relevant pools per query block. Its comments explicitly address a lazy scheduler otherwise materializing all independent score tiles. The model file is marked MIT even though the repository's general license differs. [Source](https://github.com/asher/gmlx/blob/7d5d00fff2795953846c8d9ee0c0fb3f7793ada2/gmlx/models/glm5_next/model.py#L650).

### 5. Distinguish expert residency and decode speculation

mlx-stream keeps attention, router and dense weights resident and streams missing routed experts. Separate prompt/decode resident-row budgets trade memory against misses; device hits, lookahead reads and prompt waves reduce exposed I/O. Its `requestStart` manages retained resident rows separately from token-prefix state. Such expert retention is a weight cache, not permission to persist request state. The source also records several optimizations that failed to improve served speed, including larger MLX command-buffer limits. [Expert implementation](https://github.com/davidtai/mlx-stream/blob/ac3b772b61bce66450862bca697dbb742c35453f/src/arch/glm5_next/experts.zig), [measurement and rejected-lever record](https://github.com/davidtai/mlx-stream/blob/ac3b772b61bce66450862bca697dbb742c35453f/docs/benchmarks/glm53-flash/README.md).

Native MTP can verify several draft tokens per larger matrix operation, amortizing weight reads and dispatch. It also increases the distinct experts touched per round and requires exact recurrent rollback. oMLX has `kda_decode_step`, fused MoE gate/up/down-combine, router, and sparse decode kernels; these have small-row eligibility distinct from prefill. Its recipe warns that greedy MTP output can differ due to multi-row rounding. Prompt-lookup drafting especially helps copying/editing tasks, so its numbers should not describe arbitrary generation. [Decode source](https://github.com/jundot/omlx/blob/d2fbf64f1dae14ce9384f281eca43fd9fe454e3e/omlx/patches/mlx_vlm_glm5_next_compat/decode_kernels.py), [recipe limitations](https://github.com/sethforprivacy/GLM-5.3-Flash-M5-Ultra-oMLX/blob/73939da932be68ad5412d1661776b259ecdd923c/README.md).

## Server engines: transferable structure, separate hardware

vLLM's actual `Glm5NextLinearAttention._forward` dispatches prefill to `_flashkda_prefill` when selected, otherwise `chunk_kda_with_fused_gate`; decode uses `fused_recurrent_kda`. `Glm5NextMoE` uses `FusedMoEFactory`. `Glm5NextMLAAttention` constructs the pooled indexer; NVIDIA `SparseAttnIndexerKpool.forward_cuda` invokes the accelerated pool/index operation. This demonstrates distinct prefill/decode kernels and hardware-selected fusion, not a generic claim that ordinary dense attention code is enough. The recipe requires a suitable nightly image for native GLM rendering and FlashInfer 0.6.17+ for NoPE sparse MLA. [KDA source](https://github.com/vllm-project/vllm/blob/fbb488f7d2d10e69edbcce02a4279c0046031cfb/vllm/models/glm5next/common/kda.py#L394), [MoE/model](https://github.com/vllm-project/vllm/blob/fbb488f7d2d10e69edbcce02a4279c0046031cfb/vllm/models/glm5next/common/model.py#L222), [attention](https://github.com/vllm-project/vllm/blob/fbb488f7d2d10e69edbcce02a4279c0046031cfb/vllm/models/glm5next/common/attention.py#L391), [indexer](https://github.com/vllm-project/vllm/blob/fbb488f7d2d10e69edbcce02a4279c0046031cfb/vllm/models/glm5next/nvidia/sparse_indexer.py#L741).

SGLang's decoder selects `Glm5NextLinearAttention` for KDA layers and `DeepseekV2AttentionMLA` elsewhere, with `Glm5NextMoE` expert wiring. Its DSA top-k backend can fuse selection and page-table transformation for decode/MTP verification. The cookbook chooses different expert and sparse-attention backends on Hopper, Blackwell and AMD, plus separate low-latency MTP versus throughput-oriented settings. Continuous batching, expert parallelism, HiCache and disaggregated prefill/decode target server workloads; they are not a single-stream Metal speed multiplier. [Model](https://github.com/sgl-project/sglang/blob/76b4c91360da67a2985500b82560f02278a2fff3/python/sglang/srt/models/glm5_next.py), [top-k backend](https://github.com/sgl-project/sglang/blob/76b4c91360da67a2985500b82560f02278a2fff3/python/sglang/srt/layers/attention/dsa/dsa_topk_backend.py), [cookbook](https://github.com/sgl-project/sglang/blob/76b4c91360da67a2985500b82560f02278a2fff3/docs/cookbook/autoregressive/GLM/GLM-5.3-Flash.mdx).

TensorRT-LLM's guide validates CUDA graphs, overlap scheduling, chunked prefill, MTP and hybrid cache reuse with periodic recurrent-state snapshots. These features are relevant architectural examples; the guide's minimum is 1.3.0rc29 on Blackwell. A better-scoped server number is PR #19136's 4×B200 experiment: FP8 weights, BF16 KV, random 1,024-input/1,024-output token IDs, seed 0, greedy/ignore-EOS, MTP depth 3, concurrency 1, TP4/EP4. It reports 389 output tokens/s/user, where per-user rate excludes TTFT; measured runs use 5×concurrency prompts after 2×concurrency warmup. This synthetic CUDA result cannot be compared numerically with the Mac rates. [Guide](https://github.com/NVIDIA/TensorRT-LLM/blob/04de854a9e50d920633ff0870d914263c6ba4ae7/docs/source/deployment-guide/deployment-guide-for-glm-5.3-flash-on-trtllm.md), [integration PR and protocol](https://github.com/NVIDIA/TensorRT-LLM/pull/19136).

## Bounded next experiments for Stark

These are proposed experiments, not implemented changes.

1. **Establish comparable baselines.** Try current llama.cpp and gmlx admission for the exact existing GGUF and metadata before considering conversions. Pin engine/dependency revisions and artifact hashes. Measure 96, 512, 1,221, 4,096 and 16,384 input tokens with fixed 128-token greedy output and concurrency one, plus a separately labeled sampled cell. Disable MTP and prefix reuse in the first comparison; then qualify each independently. Record load, cold TTFT, warm TTFT, prompt-only time, decode time, peak physical memory, paging and thermal/clock conditions. Do not download another 100+ GB artifact or run contenders alongside the active validation.
2. **Measure submission, then test bounded pipelining.** Use aggregate GPU timing/counters for projection GEMM, experts, KDA, mHC, DSA and waits on one prompt. Test a small bounded queue of dependent layer/chunk work only if traces show avoidable host gaps. Preserve cancellation and cleanup boundaries. Acceptance: matching logits/output hashes for the same precision, bounded in-flight workspace, correct failure cleanup, and lower cold prompt time in interleaved same-host runs.
3. **Increase token tiles and grouped expert work.** Compare T8 with a small bounded wider-tile/chunk sweep under the same GGUF and fixed memory ceiling. Reuse token rows through routing indices; fuse gate/up where formats permit. Include skewed routing, K tails and empty experts. Keep UD quant scales and rounding faithful. Acceptance: equivalent tensor results under the declared reduction policy, no paging or workspace overflow, and a whole-request prefill improvement larger than paired run spread; a faster microkernel alone does not pass.
4. **Keep F32 KDA state resident across a prompt tile.** First test convolution/L2/norm-gate fusion and register-resident F32 state while retaining current activation precision. A 40-core schedule can investigate the two-groups/core design with explicit launch and memory bounds. Acceptance: every row is updated exactly once, state and output match a matching reference under the declared arithmetic, and fresh/chunked/restored-prefix continuations pass. Include small tail chunks and cancellation. Measure its contribution after submission stalls are addressed.
5. **Qualify precision-changing M5 tensor paths separately.** Retain the existing F32 reference; specify BF16/FP16 casts, weight dequantization, F32 accumulation/state, and relaxed/TF32 policy. Test packed dense/expert GEMM and fused mHC before the long-context indexer/MLA path. For sparse kernels use prompts beyond the dense-prefix bypass, check pooled top-k near ties, and bound score/gather workspace. Acceptance: predeclared numerical and quality bounds, fresh and restored-prefix checks per artifact, controlled whole-request TTFT gains, and no memory-guard regression. An 8K chunk requires measured admission beside the 101 GiB model.
6. **Evaluate MTP after prefill is qualified.** Separate serial decode, model MTP and prompt-lookup workloads; record draft acceptance, verification widths and expert traffic. Validate recurrent rollback and restored prefix state with rejected drafts. State whether equivalence is bitwise, tolerance-based or quality-based.
7. **Keep prefix reuse within Stark's contract.** Borrow the need for joint KV, pooled-indexer, convolution and recurrent snapshots. Retain only the immediately preceding request's chunk-aligned shared prefix under matching model/context/scope/options, clearing on failure, cancellation, images and restart. Server caches or persistent SSD state do not change that policy.

No prototype speed claim should be published until a matched-artifact comparison and an independent review pass establish the claimed behavior.
