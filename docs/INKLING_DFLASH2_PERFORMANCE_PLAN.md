# Inkling 2 Mini DFlash 2 performance experiments

## What limits throughput today

On the original NVFP4/MXFP8 target on our 40-core M5 Max, DFlash 2 and DSpark emitted the same 20,825 tokens across 183 matched requests. DFlash started 5,368 rounds and DSpark started 8,588. Saving 37.5% of round starts produced a 13.2% paired throughput gain on novel prose, while DSpark led at 512, 4K and 8K on coding. The totals include zero-depth steps and exclude the initial draw from prefill. A second verifier call counts toward the same round. These measurements belong to the experimental worker. [Live benchmark and aggregate receipts](https://github.com/jshahbazi/stark/blob/a83752f22aec2139769ab8efae0d6b7729732dd1/docs/benchmarks/2026-11-24-inkling-mini-live-dflash2.md)

On the fixed 4K continuation, seven proposals yielded 4.57 output tokens per round. Stark needed 64 target calls for 42 rounds because one transaction holds four rows, including the anchor. Verification alone cost 8.52 ms per emitted token. A 1.7× gain over our 4K MLX-Serve rate of 88.7 tok/s would allow 6.63 ms per token for the entire decode. That gives us a concrete reason to investigate verifier cost. Inco’s headline compares complete engines on an M5 Pro using each engine’s preferred checkpoint. [Matched verifier replay](https://github.com/jshahbazi/stark/blob/a83752f22aec2139769ab8efae0d6b7729732dd1/docs/model-experiments/2026-11-24-inkling-mini-dflash2-traces.md) · [Inco’s comparison](https://x.com/inco_ai/status/2125066128968007863)

## Experiments in order

| Experiment | First measurement | Decision |
| --- | --- | --- |
| Recover the live time breakdown | The worker already times drafting, verification and commit. Collect those aggregates directly on alternating prose and 4K runs with DSpark and DFlash. Count second verifier calls and report milliseconds per emitted token. The previous benchmark adapter retained round counts and omitted the stage clocks. | Attribute the cost on the workloads where the winner flips. Split feature transfer from MLX execution if the combined draft time warrants it. |
| Choose draft depth per round | Replay the saved proposals with a choice of three or seven drafts based on recent acceptance and measured round cost. Compare with fixed three and fixed seven on held-out traces, then time the best policy in the worker. The DSpark planner currently caps depth at three. DFlash still computes all seven candidates when the verifier uses a shorter prefix. | Keep a policy only if it improves live decode against fixed seven and the workload breakdown supports where to enable it. The existing fixed-width screen gained just 2.6% moving from three to seven. |
| Prototype an eight-row native verifier | Start with a single straight-line candidate block. Widen the Metal buffer bindings, scratch storage and rollback state together. Compare with conditional four-row transactions on the same proposals, including early rejection. The existing eight-row diagnostic runs two calls. | Compare total target time per emitted token. A wide pass can save a second call on long accepted prefixes and waste work on short ones. Check every committed prefix against serial execution, including the next logits and restored state. |
| Keep target features and drafting on the GPU | Time feature capture, host copies, IPC, draft KV updates and selection separately. The current warm draft call including IPC was 8.71 ms on prose and 9.39 ms at 4K. Prototype GPU-resident feature exchange where the breakdown shows avoidable cost. | Use measured end-to-end savings to decide how much of the MLX companion to replace. Preserve the trained feature taps, selector arithmetic and prefix restoration. |
| Verify alternative continuations | Use recorded candidate alternatives where available, or capture a small private replay. Estimate extra accepted tokens per additional verifier row against the best single-chain policy. Splash uses a candidate tree and prices verifier rows from observed costs. | Prototype tree verification only if the measured row costs support it. Each accepted branch must commit the correct KV and convolution state and discard sibling state. [Splash runtime](https://github.com/incoai/splash/blob/2afc7337aacc044722fa95e4cb3da75c281a19a8/runtime/model/Runtime.cpp#L2541-L2591) |

## Effort and qualification

Allow hours for stage timing and a first adaptive-depth screen. A first timing for a wider verifier may be possible within a working day. Allow several days for a correctness-tested prototype. GPU-resident drafting and branching verification are separate implementation projects whose scope depends on the measurements above. These are AI-assisted engineering estimates. The previous full three-engine benchmark occupied the M5 Max for 28 minutes.

For a candidate that passes the screen, repeat the [performance playbook](PERFORMANCE_PLAYBOOK.md) comparison with the same original checkpoint, quantization, greedy policy, image-loaded worker, prompts and output caps. Alternate run order on AC power and report paired results by workload. Verify output hashes, serial parity after rejection, exact prefix restoration, and image and cancellation invalidation. Keep fixed-seed sampled parity for changes that share the sampled path. Record the build, private receipt hashes and promotion decision with the dated experiment. The first two experiments can use the existing branch and fixtures before committing to new Metal kernels.
