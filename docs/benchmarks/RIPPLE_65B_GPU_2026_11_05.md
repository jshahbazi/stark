# Ripple-65B native GPU performance, 2026-11-05 UTC

Ripple Q8 decode improved from **2.760 to 6.040 tok/s (2.19×)** on the
128 GiB Apple M5 Max. Median warm prefill for the fixed ten-token input fell
from **3.438 to 1.544 seconds**. All generated-token hashes agree across the
baseline and optimized runs. The signed app build was tested, installed and
left running with Ripple selected.

These are short, unscreened observations on this Mac. The comparison uses a
fresh baseline executable; the different desktop load in the
[initial validation](RIPPLE_65B_NATIVE_2026_11_04.md) is not its denominator.
This report supersedes those Ripple timing observations for this workload.
The earlier source-bound numerical and test records remain unchanged.

[Machine-readable evidence](data/ripple-65b-gpu-2026-11-05.json) contains
individual timings, executable identities, reference errors and diagnostic
counters. Private fixtures, weights and runtime artifacts remain ignored.

## Architecture and change

The publisher describes Ripple as a
[Gemma 3N-like dense Transformer developed from an OLMo 3 baseline](https://huggingface.co/ricursiveAI/Ripple-65B-Preview/blob/e27e171792f303d74c048184e8259ba663cfa0d5/README.md).
The released architecture is `ricursive`: 80 layers, hidden width 5,120,
FFN width 40,960, 80 query heads and eight KV heads of dimension 128. Four
sliding/RoPE layers alternate with one global/NoPE layer. Ripple also requires
four normalization stages, attention gates, fixed embedding-conditioned value
residuals and asymmetric SwiGLU clipping.

The native implementation now keeps normalization, attention, gates, residuals
and FFN activations on Metal through each token. It reuses Stark's deferred
graph and packed matrix primitives, with Ripple-specific control kernels.
Q8 projections use the existing two-row grouped kernel on six measured
geometries. Selection is local to Ripple's graph. Weight bytes, F32 activation,
accumulation and cache precision, and Safe Metal math are retained; reduction
grouping changes.

Complete weight-view admission gates the graph. A declined inventory retains
staged execution and its bounded streaming cache. KV allocations grow with the
prefix, with ring storage for sliding layers. The 32 GiB cache bound includes
persistent attention workspace and temporary old/replacement cache storage.
Reset and failure release request state. Prefill still advances one token at a
time; this change does not implement batched prefill or speculative decoding.

## Fixed comparison

- Checkpoint: `AtomicChat/Ripple-65B-Preview-GGUF`, Q8_0,
  `57066fdb2348a53f2261f096e0a793b9554b4106`; two shards, 68,840,113,568 bytes.
- Metadata/reference: `ricursiveAI/Ripple-65B-Preview`,
  `e27e171792f303d74c048184e8259ba663cfa0d5`.
- Baseline checkout: `203ce69e27f25daeb6f0e36eb4755f32e8f65937`, with engine
  code from `4cb209cdb638ee5d8107cd50eb128bacabbef25b`.
- Candidate code: `1978a3b17df1ea83b4d7e1139ec2e91619f2acfc`.
- Rust 1.98.1 release builds, locked dependencies, generator and optimized
  scorer built in separate Cargo invocations.
- Apple M5 Max, `Mac17,7`, 18 CPU cores, 40 GPU cores, 128 GiB unified memory;
  macOS 26.7.1. This work did not change power settings.

Four worker processes ran serially in baseline/candidate/candidate/baseline
order. Each process handled three identical requests: one warmup and two
measurements. The candidate arm combines two measurements from the unsigned
worker and two from its signed app worker. The signed-only median is also
6.040 tok/s. The baseline executable was preserved before edits; its identity
comes from its hash, independently of the later harness checkout.

Every request uses the same ten input tokens, context boundary 512, greedy
sampling and a 32-sampled-token limit. Every request ends at that limit.
Decode rate is `31 / decode_seconds`, since prefill supplies the first sample.
Config, tokenizer metadata, template, input digest and verified weight receipt
match across all four cohorts. Previously verified weight hashes are retained;
size, modification time and inode are checked before and after each cohort.

| Four measured requests per arm | Baseline | Candidate |
| --- | ---: | ---: |
| Median decode tok/s | 2.760 | 6.040 |
| Observed decode range | 2.560–2.801 | 5.521–6.545 |
| Pooled decode tok/s | 2.717 | 6.014 |
| Median ten-token prefill seconds | 3.438 | 1.544 |
| Median complete request seconds | 14.669 | 6.712 |

Median decode improved 118.8%; median prefill time fell 55.1%, and median
request time fell 54.2%. All twelve requests have the same generated-token
identity hash. The small sample, shared desktop and short context do not
establish a general throughput floor, maximum or long-context speed.
Candidate warmup prefills still take 17.5–21.6 seconds, including initial
weight preparation; those requests are excluded from the warm comparison.

## Diagnostic evidence

A separate instrumented replay uses ten synthetic input tokens and sixteen
decode steps, with the same output hash in both implementations. Baseline
decode has 5,136 GPU submissions/readbacks. Candidate decode has 96 submissions:
sixteen token graphs plus eighty layer-cache growth copies at one capacity
boundary. Only sixteen readbacks remain. Its counters record 10,256 grouped
Q8 projections, verifying effective dispatch on the real checkpoint.

Synthetic rotating-bank ABBA tests selected the grouped Q8 kernel from five
candidates. Median GPU matrix times changed as follows:

| Projection | Scalar µs | Grouped µs |
| --- | ---: | ---: |
| Attention Q/gate | 183.0 | 116.6 |
| Attention K/V | 24.4 | 18.8 |
| Attention output | 178.3 | 118.2 |
| FFN gate/up | 683.7 | 399.0 |
| FFN down | 666.0 | 485.7 |
| Vocabulary head | 1,643.0 | 940.9 |

These component timings predate promotion and are labeled accordingly in the
aggregate. Their test body is unchanged, but the first timing executable was
not sealed before rebuilding policy tests. They are diagnostic evidence;
the source-bound worker comparison above supplies the end-to-end result.

## Numerical and worker validation

The unchanged independent full reference decodes the same Q8 weights and runs
all eighty publisher layers with CPU PyTorch F32 execution. Eight native
full-vocabulary readouts pass `0.001 + 0.001 * abs(reference)`:

| Full Q8 comparison | Result |
| --- | ---: |
| Maximum absolute error | 0.0002145767 |
| Mean absolute error | 0.0000418464 |
| Relative L2 error | 0.0000027670 |
| Greedy agreement | 8/8 |

The seventeen-position source fixtures pass for F32, BF16 storage/F32 execution
and Q8 storage, including sliding eviction and global attention. Their largest
absolute error is 0.0000055284, within the unchanged `2e-5` absolute/relative
bound. Reset replay, invalid-token rejection and recovery pass.

An additional forty-position four-channel stress fixture nearly cancels its
residuals. Its F32 graph and staged paths reach respective maximum errors of
0.0008179 and 0.0012465 against an independent F64 oracle; both remain separately
tested under a 0.002 bound. A stable extended fixture retains a strict `2e-5`
check and reaches only 0.0000002159 graph/F64 error. These checks do not qualify
whole-model BF16 quality, agent competence or long-context quality.

Checks recorded separately by source revision:

- `410bec76`: physical CPU/Metal engine suite, 774 passed and 79 ignored;
  seven integration tests and three doctests passed.
- `1978a3b1`: final focused suite, twelve passed and one ignored, including
  rejected-inventory fallback, ring/growth parity, reset, nonfinite input and
  Q8 policy/failure checks. Repository policy and formatting passed.
- Final signed workers: tiny Q8 generation/scoring integration passed,
  including consecutive-cache isolation and failure recovery. Maximum candidate
  score error is 0.0000012517. This synthetic integration fixture adds tokenizer
  metadata and is separate from the full-model timing workload.
- Final signed full-checkpoint worker: arithmetic, literal instruction,
  intervening-request isolation and rejected-request recovery passed. These
  elementary replies end after one or two output tokens and are functional checks.

The signed functional check reports peak Metal allocation of 68,398,841,856
bytes (63.701 GiB) and peak worker RSS of 212,025,344 bytes. Shared/file-backed
accounting prevents adding those values to infer physical memory use.
System-wide swap-out increased 2,572,288 bytes; it cannot be attributed to the
worker. No allocation failure occurred.
