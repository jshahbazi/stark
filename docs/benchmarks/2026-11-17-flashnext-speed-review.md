# Flash Next prefill and decode opportunities

**20261117-FLASHSPEED-01 · November 17, 2026 · Installed-worker observation and source review**

For a coding agent, the largest observed opportunity is eliminating repeated prefill. An 8,714-token request took 4.93 s to deliver its first text after an unrelated request displaced its prefix. Its immediate repeat took 0.54 s and reused 8,192 tokens. For fresh input, the best kernel lead is the grouped expert gate/up path. For decode on Lily Q4-XL, the first kernel to try is packed-weight reuse in the hyper-connection (HC) reads during exact multi-token prediction (MTP) verification. Both kernel candidates await implementation and measurement.

## What ran

The installed Stark 0.22.1 HTTP server served 41 serialized text requests on its already loaded Lily Q4-XL worker. The machine was an M5 Max with 128 GiB on AC, macOS 26.7.2. This was an ordinary desktop session. There was no quiet-host screen, GPU-clock sampling or per-request swap telemetry. The worker had image support and prefix caching enabled. Model discovery reported MTP enabled by default, two recommended drafts, three maximum and exact batched verification. The HTTP tests set MTP explicitly. Per-round proposal and acceptance counts were unavailable through this endpoint.

The live worker executable's inode matched the hashed installed file, SHA-256 `9a3a4fac1f5c15124b913667260df7c33f9b35508ca988a65b6386e08c3a4707`. Local model metadata identifies `fabiogreter/Qwen3.8-Flash-Next-lily-q4-xl@0f94842e3682b49acace4daeb4cf2e65a6f94f83`, with Q4 GDN and Q8 attention/shared expert/head/embedding. The mounted weights comprised 55 shards and 106,905,155,192 bytes. This run checked metadata and sizes. The static findings use main at `2cc73453`. This run did not rehash the weight contents or rebuild the installed worker from that commit. ## Repeated prefill over HTTP

Two synthetic test-vector lists were repeated three times each. A separate sequence grew list A, switched to an unrelated list B, then returned to the identical grown A. Inputs used the same credential, settings and loaded worker. Each response used a 12-token output cap. Time is from starting the HTTP request to its first nonempty streamed text. It includes templating, tokenization, cache handling, prefill, initial sampling and transport.

| Request | Prompt tokens | Cached tokens | First text, seconds |
| --- | ---: | ---: | ---: |
| Short list, then two repeats | 2,513 | 0 / 0 / 0 | 1.24 / 1.13 / 1.23 |
| Long list, then two repeats | 6,263 | 0 / 4,096 / 4,096 | 3.44 / 1.31 / 1.32 |
| A, then A with more rows | 7,704 / 8,714 | 0 / 4,096 | 3.18 / 2.61 |
| B | 7,994 | 0 | 4.30 |
| Grown A again, then its immediate repeat | 8,714 / 8,714 | 0 / 8,192 | 4.93 / 0.54 |

The three grown-A outputs shared one text hash. Stark retains one immediately preceding prefix. For the Lily hybrid backend, the worker asks the loaded model for its chunk size. Lily sets this to 4,096 tokens. The saved boundary is the start of the final chunk, with at least two tokens left in a resumed request. Restoring a recurrent snapshot also relies on the corresponding KV rows remaining valid. [Boundary calculation and hit checks](../../crates/stark-generate/src/prefix_cache.rs) · [Worker lifetime](../../crates/stark-generate/src/hybrid.rs) · [Lily restore](../../crates/stark-engine/src/engine/hybrid/lily.rs)

**First experiment.** Compare 1,024-, 2,048- and 4,096-token prefill chunks at 8K, 12K and 32K on both fresh inputs and growing agent transcripts. The current engine couples snapshot boundaries to chunk geometry. A measurement harness can use Lily’s existing chunk-size setter. Only a test currently calls it. A finer grid can save repeated work and also slow fresh prefill or lose a hit where a transcript diverges. Test fresh versus resumed output and state within each configuration, including the official pack's final-token holdout, cancellation, images and MTP changes. Record cold throughput, first-text latency, cache hits and peak memory. [Chunk policy](../../vendor/lily-core/src/qwen4exp/model.rs) · [Existing exactness controls](../archive/runs/2026-11-02-hybrid-prefix-reuse.md)

In a retained real OpenWork session, the 17 follow-ups processed 91,860 uncached tokens. If each shared prefix had extended to the finer boundary, a 2,048 grid could have saved **up to 28,672 additional tokens (31.2%)**, or a 1,024 grid up to 40,960 (44.6%). These are upper bounds computed from previous and current prompt lengths. The receipt proves prefix identity only through the boundary actually reused. [OpenWork per-turn counts](../archive/runs/2026-11-02-openwork-qwen38-live-prefix-reuse.md)

**Larger architectural option.** Give two interleaving conversations independent resident prefix state under a strict byte budget. This requires changing Stark's current immediately-previous-request policy. Each entry needs a credential-scoped conversation identity, exact token-prefix verification, its own valid KV pages and recurrent state, and eviction under memory pressure. A second snapshot handle alone cannot restore overwritten KV. Replay A–B–A alongside single-session and low-memory controls before extending capacity. [Current cache contract](../../AGENTS.md)

## Decode over HTTP

One 46-token coding prompt requested an implementation, tests and cancellation behavior. Each decode cell had one excluded warmup per route followed by four off/on pairs in balanced order. All had zero reused input tokens. For sampled runs, temperature was 1, top-k 20, top-p 0.95 and seed 42. Greedy runs used temperature zero. Thinking was disabled. The HTTP rate is the sum of output tokens after the first divided by the sum of the first-to-last text-delta intervals. Every measured 96-token response delivered 96 nonempty deltas. Wall time includes the entire request.

| 96-output cell | MTP off, HTTP tok/s | MTP on, HTTP tok/s | Median wall seconds, off / on | Output comparison |
| --- | ---: | ---: | ---: | --- |
| Sampled | 62.66 | 76.32 | 1.826 / 1.514 | Stable within each route, different across routes |
| Greedy | 61.75 | 66.51 | 1.774 / 1.742 | Same text hash across both routes |

At the original 256-token cap, sampled MTP stopped at 127 tokens in every run and MTP off hit the cap in every run. That comparison mixes answer length with speed. The subsequent 96-token cells match emitted work. The greedy result is the cleanest same-output comparison. These are client-observed rates on one prompt. Native kernel timing, task correctness and a general draft-depth policy remain unmeasured here. A prior 128-request baseline found that even the sign of a draft-depth benefit changes with prompt and sampling. [Prior workload matrix](2026-11-15-llama-v1-flashnext-lily-assessment.md)

## Kernel experiments in priority order

1. **Cold prefill on Lily.** At 4K rows the routed MoE already sorts expert assignments and performs grouped Q4 matrix multiplies. It still writes gate and up outputs separately, then rereads both for SwiGLU. At 4,096 rows, 10 routes per token and 640 BF16 values per route, those two arrays total **100 MiB per layer** before the reread. Profile 4K, 8K, 32K and one long natural prompt. Expose the chunk counters for n-gram staging, host encoding, GPU work and waits, then time the grouped stages. If gate/up is material, fuse the projections and activation on a shared tile while preserving the intermediate rounding and routing order. Register pressure or reduced occupancy could erase the gain. The byte count is logical storage. The previous withdrawn small-row decode fusion tested a different kernel. [Grouped path](../../vendor/lily-core/src/moe_ffn.rs) · [Chunk counters](../../vendor/lily-core/src/stats.rs) · [Withdrawn decode experiment](2026-11-07-flashnext-moe-projections.md)
2. **Lily exact MTP decode.** Start with the Q8 HC down projection in the verifier. Each verifier row reloads and unpacks the same weights in separate GPU threadgroups. The prefill shader already contains a multi-row template that shares those loads. Apply that technique to two and three verifier rows, preserving each row's normalization, reduction order and BF16 boundaries. Try the up projection only after the down projection wins. Before the November 16 change, instrumented long responses to 20- and 24-token prompts attributed 15.76–16.29% of decode to all HC work. Its share at long input lengths is unknown. Even halving that whole bucket would imply about 9% faster decode on those workloads. Reprofile the current build and compare useful decode and complete latency at 4K and long context, with matched output and MTP work. [Verifier HC selection](../../vendor/lily-core/src/qwen4exp/model.rs) · [Row kernels and templates](../../vendor/lily-core/src/kernels/metal/hc.metal) · [Lily stage measurements](2026-11-15-lily-small-row-verifier.md)
3. **Higher-risk decode experiment.** Exact verification currently captures a full intermediate F32 Gated DeltaNet state after every verifier row except the last. A normal two-draft round writes two snapshots across 36 layers and 48 heads of 128×128 values, or **216 MiB** of logical intermediate writes. Measure full-accept, partial-accept and interrupted rounds separately. A candidate could keep the pre-round state intact, publish the final state by swapping buffers on full acceptance, and replay only the retained prefix from compact recurrence operands on partial acceptance. Keep the pre-round state until streamed delivery commits. Rejection-heavy workloads could lose. Validate subsequent token scores, state, EOS and interrupted delivery. The historical time labelled rollback bounds only the finish step. The proposed saving also includes writes during verification. [Capture layout](../../vendor/lily-core/src/qwen4exp/model.rs) · [Rollback](../../vendor/lily-core/src/qwen4exp/spec.rs)

The mixed-4/8-bit MLX-Serve pack also runs on Stark. It shares the host verification loop and selects pack-specific exact kernels and rounding. Its historical 4K, two-draft study measured 56.69 → 65.02 native decode tok/s. For that pack, test the existing 64-row grouped MoE tile on long prefill, where the official route currently selects 32. For decode, its Q8 GDN input/output projections dispatch each verifier row independently, giving a separate opportunity to share packed loads. Benchmark that checkpoint independently. [Mixed-pack measurements](QWEN38_OFFICIAL_BATCHED_MTP_2026_10_31.md) · [Tile selection](../../vendor/lily-core/src/kernels/quant.rs) · [Q8 GDN projection](../../vendor/lily-core/src/kernels/official_q8_projection.rs)

For an external comparison, the Lily fork reports 2,413 prefill tok/s and 80 plain or 100 two-draft decode tok/s on Q4-XL at 4K, with 256 greedy tokens over HTTP on an M5 Max. Its 4K real-text corpus and timing protocol differ from the short coding probe here. Using identical input token IDs, output budgets, precision, sampling and timing boundaries on both engines would measure the gap under matched conditions. [Upstream Lily benchmark and methodology](https://github.com/fabiogreter/lily-qwen3.8-flash-next#performance)

For scale, the already-merged verifier change measured 72.93 → 76.96 useful native decode tok/s on 88,398 input tokens. Prefill consumed about 44 of 62 request seconds. The paired whole-request improvement was 2.39%, and the prefill difference was within baseline variation. Earlier sustained tests also saw the unchanged baseline fall from 95.46 to 82.20 tok/s over consecutive requests. Interleave candidate and baseline on the same checkpoint, capture GPU timing and host conditions, and report time to first text and complete-request latency alongside useful decode.
